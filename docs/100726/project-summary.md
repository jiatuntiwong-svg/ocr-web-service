# SaaS: สร้างเอกสาร Word/PDF จำนวนมากจาก Excel + Template

## 1. แนวคิดหลัก

รับ template `.docx` ที่มี placeholder (`{{ full_name }}`) จากผู้ใช้ + ข้อมูล `.xlsx`
แต่ละแถวใน Excel = เอกสารหนึ่งฉบับ ผลลัพธ์เป็น `.docx` และ/หรือ `.pdf`

**ตลาดเป้าหมาย:** เอกสารที่ฟอร์แมตแตะไม่ได้และไม่มี SaaS ไทยทำอยู่ — หนังสือรับรองเงินเดือน/การทำงาน,
ใบประกาศนียบัตร/วุฒิบัตรอบรม, สัญญาจ้าง/เช่า, หนังสือราชการ

**จุดยืนสำคัญ:** ไม่แข่งกับ FlowAccount/PEAK ในตลาดใบกำกับภาษี (เขาได้เปรียบเรื่อง compliance/e-Tax
มากเกินไป) — เล่นตลาดที่ต้องใช้ฟอร์แมต `.docx` ของลูกค้าเองเท่านั้น

---

## 2. สถาปัตยกรรม — หัวใจของทั้งโปรเจกต์

```
Browser (client-side ทั้งหมด)
  ├─ unzip .docx (JSZip) → แก้ document.xml/header/footer → zip กลับ
  ├─ อ่าน .xlsx (SheetJS)
  ├─ preview สด (docx-preview) — re-render ทุกครั้งที่เปลี่ยน mapping
  └─ ดาวน์โหลด .docx ทีละไฟล์ หรือ zip ทั้งชุด
        │
        │  (เฉพาะตอนขอ PDF เท่านั้น)
        ▼
   Server: Queue → Worker → Gotenberg/LibreOffice → PDF → S3 (TTL 24h)
```

### ทำไมถึงสำคัญ
- **.docx ทั้งหมดทำในเบราว์เซอร์ ต้นทุนเป็นศูนย์** ไม่ต้องมี server เลย
- **ข้อมูลลูกค้า (เงินเดือน, เลขบัตรประชาชน) ไม่ออกจากเครื่อง** จนกว่าจะขอ PDF — จุดขายที่คู่แข่ง cloud-only ไม่มี
- Server มีหน้าที่แค่ 3 อย่าง: auth, เก็บไฟล์ชั่วคราว, แปลง PDF
- **โครงสร้างต้นทุนนี้ = โครงสร้างราคา** (ดูหัวข้อ 6)

### ข้อจำกัดของสถาปัตยกรรมนี้
- โควตาการใช้งาน **บังคับไม่ได้** สำหรับสิ่งที่ทำในเบราว์เซอร์ (.docx) — บังคับได้เฉพาะสิ่งที่ผ่าน server (PDF, template ที่เก็บบนคลาวด์, ส่งเมล)
- generate จำนวนมาก (500+ แถว) กิน RAM ฝั่งเบราว์เซอร์ ต้องมีเพดาน (~300 แถว) แล้วผลักงานใหญ่ขึ้น server

## 3. Prototype ที่ทำไปแล้ว

ไฟล์: `docx-merge-prototype.html` — ไฟล์เดียวจบ ไม่ต้อง build ไม่ต้องมี server

**ทำได้แล้ว:**
- อ่าน placeholder จาก `document.xml` + header/footer ทุกส่วน
- **merge adjacent runs** ก่อนแทนที่ — แก้ปัญหา Word ฉีก `{{ full_name }}` เป็นหลาย run
- preview สดพร้อมไฮไลต์ (ฟ้า = แทนที่แล้ว, เหลือง = ยังไม่จับคู่) ผ่าน `docx-preview`
- auto-map คอลัมน์ไทย ↔ placeholder อังกฤษด้วย synonym dictionary
- filter ภาษาไทย: `thai_date` (พ.ศ.), `baht_text` (จำนวนเงินเป็นตัวหนังสือ), `comma`, `thai_digit`
- generate ทั้งชุดเป็น `.zip` ฝั่ง client ล้วน
- guard: ปฏิเสธไม่ส่งไฟล์ที่ยังมี `{{ }}` ค้างอยู่
- ปุ่มดาวน์โหลดไฟล์ตัวอย่าง (template + data) สร้างสดในเบราว์เซอร์เพื่อทดสอบ

**บั๊กที่เจอและแก้แล้ว:**
- `substitute()` เดิมมีสองเส้นทาง (preview vs download) ที่ไม่ตรงกัน — ตอน download จะกิน "tail"
  ของ text ในบาง edge case (placeholder อยู่ใน run เดียว + ไม่มีไฮไลต์) ทำให้ **preview ถูกแต่ไฟล์จริงผิด**
  โดยไม่มีใครสังเกต แก้โดยรวมเป็น path เดียว ต่างกันแค่ตัวแปร `color`
- เพิ่ม post-render assertion: สแกนหา `{{`/`}}` ค้างก่อนปล่อยไฟล์

**ยังไม่ทำ:**
- ตั้งชื่อไฟล์จาก pattern ที่ผู้ใช้กำหนด (`{{ ref_no }}-{{ full_name }}`) + กันชื่อซ้ำ/ชื่อสงวนของ Windows/`/` ในชื่อไฟล์
- Conditional content (`{% if %}`) ระดับย่อหน้า/แถวตาราง
- สลับ template ทั้งไฟล์ตามเงื่อนไข (paid feature)
- Web Worker + cache XML ที่ parse แล้ว เพื่อลด RAM ตอน generate จำนวนมาก
- ส่งเมลแนบไฟล์ (ดูหัวข้อ 8 — ตัดสินใจเลื่อนออกไปก่อน)

## 4. ปัญหาเทคนิคที่ระบุไว้และวิธีแก้

| ปัญหา | สาเหตุ | ทางแก้ |
|---|---|---|
| PDF เป็น □□□□ | ฟอนต์ไทยไม่มีใน container | ลง TH Sarabun New, Sarabun, fonts-thai-tlwg + `fc-cache` |
| ฟอนต์ Angsana/Cordia | ลิขสิทธิ์ Microsoft ห้ามฝังใน container โดยไม่มี license | font substitution (`local.conf`) + ให้ผู้ใช้อัปโหลดฟอนต์เอง + เตือนตอน upload template |
| placeholder ถูกฉีกหลาย run | Word ฉีก run เวลาพิมพ์/ลบกลางคำ | normalize runs ก่อน render (merge run ที่ format เดียวกัน) |
| ข้อความซ้ำ/ค้างในเทมเพลต | track changes ไม่ accept, hidden text (`w:vanish`), ฟอนต์/สีขาว | ตรวจตอน upload: สแกน `w:del`, `w:vanish`; แนะนำให้ Accept All Changes |
| `/` ในเลขที่เอกสารไทย (`HR-2568/0141`) | ตีความเป็น path separator ใน zip | sanitize ชื่อไฟล์ก่อนใส่ zip |
| PDF ช้า/กิน RAM | LibreOffice ไม่ thread-safe, 1 process ต่อไฟล์ | merge N แถวเป็น .docx เดียว → แปลงทีเดียว → หั่นด้วย token ที่ฝังใน footer |
| LibreOffice ค้าง/บวม | ไม่ใช่ server-native | ใช้ Gotenberg, restart ทุก 100–200 conversion, hard timeout+SIGKILL, tmpfs |

## 5. Stack ที่แนะนำ

- **.docx generation:** ทำในเบราว์เซอร์ (JSZip + DOM parsing) — ไม่ต้องเลือก server language เพื่อสิ่งนี้
- **Server (auth, storage, PDF orchestration):** Python (FastAPI) หรือ Node — ต่างกันไม่มากเมื่อไม่ต้องใช้ image-merge library ที่มีปัญหา license (`docxtemplater` core ฟรี, module รูปภาพเสียเงิน; ทางเลือก Node: `docx-templates` ซึ่ง MIT ฟรีทั้งหมด)
- **PDF conversion:** Gotenberg (ห่อ LibreOffice headless มาให้พร้อม queue/timeout handling) — อย่าเขียน wrapper เอง
- **Queue:** Celery (Python) / BullMQ (Node)
- **Storage:** S3-compatible, TTL 24 ชม., presigned URL

## 6. Capacity & ต้นทุน server (ประเมิน ballpark)

หน่วยคิดคือ **job** (= 1 conversion หลังรวมไฟล์) ไม่ใช่จำนวนแถว

| เครื่อง | concurrent PDF conversion | job/ชม. โดยประมาณ (ใช้เทคนิครวมไฟล์) |
|---|---|---|
| 2 vCPU / 4 GB | 2 | ~350 |
| 4 vCPU / 8 GB | 4 | ~700 |
| 8 vCPU / 16 GB | 8 | ~1,400 |

**กฎจำง่าย:** `concurrency = min(vCPU, (RAM_GB - 2) / 0.4)` — LibreOffice กิน 150–400 MB/process

**สรุป:** VPS เริ่มต้น (2 vCPU/4GB, ~$20–25/เดือน) รองรับลูกค้าหลักสิบถึงหลักร้อยรายได้ถ้าทำเทคนิครวมไฟล์
ตั้งแต่วันแรก — ไม่ทำ throughput จะต่ำกว่านี้ราว 10 เท่า

**ต้องมีเสมอ:** queue แยกตาม tenant (กัน job ใหญ่บล็อกคนอื่น), autoscale-to-zero, progress + อีเมลแจ้งเสร็จ

## 7. โมเดลราคา (ร่างเริ่มต้น — ต้องทดสอบกับตลาดจริง)

**Metric หลัก: จำนวน PDF/เดือน** (ไม่ใช่ seat ไม่ใช่ job) เพราะตรงกับทั้งคุณค่าที่ลูกค้าได้และต้นทุนจริง

| | Free | Pro | Team | Business |
|---|---|---|---|---|
| ราคา/เดือน | 0 | ~590฿ | ~1,900฿ | ~6,900฿ |
| PDF/เดือน | 30 | 1,000 | 5,000 | 25,000 |
| Word (.docx) | **ไม่จำกัด** | ไม่จำกัด | ไม่จำกัด | ไม่จำกัด |
| Template บนคลาวด์ | 1 | 10 | ไม่จำกัด | ไม่จำกัด |
| จำ column mapping | ❌ | ✅ | ✅ | ✅ |
| ผู้ใช้ | 1 | 1 | 5 | ไม่จำกัด |
| เพิ่มเติม | — | ลบ watermark | แชร์ template, เวอร์ชัน, สลับ template ตามเงื่อนไข | อัปโหลดฟอนต์เอง, PDF ผ่าน Word จริง (Graph API), SSO, audit log |

**หลักการที่ยึด:**
- สิ่งที่บังคับไม่ได้ (ทำในเบราว์เซอร์) = ให้ฟรีไม่จำกัด → Word, การใช้งานทั่วไป
- สิ่งที่บังคับได้ (ผ่าน server) = คิดเงิน → PDF, template ที่เก็บบนคลาวด์, ส่งเมล, team/SSO
- อย่าให้ PDF ไม่จำกัดในทุก tier — มีความเสี่ยงลูกค้ารายเดียวกิน margin ทั้งหมด ใช้ overage pack แทน
- ตลาดองค์กร (บริษัทใหญ่ที่มี Excel เงินเดือน/ข้อมูลอ่อนไหว) ควรเป็น "ติดต่อฝ่ายขาย" ไม่ใช่ self-serve —
  ขายเป็น on-prem/VPC ได้ง่ายเพราะสถาปัตยกรรม client-side ทำให้ deploy เบา (แค่ Gotenberg + worker)

## 8. ฟีเจอร์ที่พิจารณาแล้ว "ยังไม่ทำตอนนี้"

**ส่งอีเมลแนบไฟล์อัตโนมัติ** — ตัดสินใจ**เลื่อนออกไป**เพราะ:
- ต้องขึ้น server เสมอ (SMTP credential) → เสียจุดขายเรื่องข้อมูลไม่ออกจากเครื่อง
- เอกสาร (เงินเดือน/สัญญา) ส่งผิดคนแล้วเรียกคืนไม่ได้ ต่างจาก generate ไฟล์ผิดที่ลบทิ้งได้
- ปัญหา deliverability/domain reputation จริงจัง
- ถ้าจะทำ ควรทำแบบ OAuth เข้าบัญชีอีเมลของลูกค้าเอง (ไม่ใช่ส่งจากโดเมนตัวเอง) พร้อม audit log เต็มรูปแบบ
  เก็บเป็น tier บนสุด

**Conditional content / สลับ template ตามเงื่อนไข** — แยกเป็น 3 ระดับความซับซ้อน:
1. ซ่อนบางบรรทัด (`{% if %}`) — ควรทำเป็น**ของฟรี** เพราะเป็นสิ่งที่ template engine ควรมีอยู่แล้ว และทำในเบราว์เซอร์ ไม่กินต้นทุน
2. สลับข้อความ (`{% if %}...{% else %}`) — ฟรีเช่นกัน
3. สลับ template ทั้งไฟล์ตามกฎ — เหมาะเป็น **paid feature** เพราะต้องเก็บหลาย template + กฎ + mapping ข้ามไฟล์บน server จริง

ลำดับที่แนะนำ: อย่าเพิ่งทำจนกว่าจะมีผู้ใช้จริงมาขอ

## 9. ฟีเจอร์ "ว้าว" ที่ไม่กินทรัพยากร (ต่อยอดจาก client-side)

เรียงตามความคุ้ม (ผลกระทบ / ความยาก):

1. **รายงานตรวจ template อัตโนมัติตอน upload** — รวมเช็คที่มีอยู่แล้ว (font, track changes, ข้อความค้าง, placeholder ครบไหม) เป็นหน้าเดียวแบบ "เกรด" — แนะนำทำก่อน
2. **Anomaly detection ทางสถิติ** — ตรวจ outlier ในคอลัมน์ตัวเลข/วันที่ก่อน generate (mean/stddev ธรรมดา) — แนะนำทำคู่กับข้อ 1
3. Diff view เทียบรอบ generate ก่อนหน้า (เหมาะกับสลิปเงินเดือนรายเดือน)
4. Keyboard-driven review (↓ / A / F) สำหรับเช็คหลายร้อยแถวเร็วขึ้น
5. Search/filter ข้ามหลักพันแถวแบบ instant (ไม่มี round-trip เพราะข้อมูลอยู่ใน memory อยู่แล้ว)
6. Template gallery พร้อมข้อมูลปลอม preview ได้ทันทีโดยไม่ต้องอัปโหลด

## 10. สถานะตลาด (จากการค้นเว็บเบื้องต้น — ยังไม่ยืนยันด้วยการคุยกับผู้ใช้จริง)

- **ไม่พบ SaaS ไทยที่ทำงานนี้โดยตรง** — มีแต่บทความสอน mail merge ของ Word (จากมหาวิทยาลัย/บล็อก Excel)
  และธุรกิจโรงพิมพ์ที่รับ "พิมพ์เกียรติบัตรพร้อมรันชื่อ" (บริการ ไม่ใช่ซอฟต์แวร์)
- **คู่แข่งจริงคือต่างชาติ**: Documentero ($19/เดือนสำหรับ 100 เอกสาร ถึง $299/เดือนสำหรับ 10,000),
  Docupilot, Formstack Documents, EDocGen, Docmosis — ไม่มีเจ้าไหนรองรับภาษาไทย (พ.ศ., บาทเป็นตัวหนังสือ,
  ฟอนต์ไทย, เลขที่หนังสือราชการ)
- **ตีความสองทางที่ยังตอบไม่ได้จากการค้นเว็บ:** (ก) ช่องว่างจริงที่ยังไม่มีใครทำ หรือ (ข) เคยมีคนลองแล้วตลาดไม่จ่าย
  ต้องยืนยันด้วยการคุยกับผู้ใช้จริงเท่านั้น

## 11. ความเสี่ยงและสิ่งที่ต้องระวัง

- **PDPA** — ข้อมูลลูกค้าใน Excel (เงินเดือน, เลขบัตรประชาชน) ต้องมี retention policy ชัดเจน, auto-delete,
  DPA สำหรับลูกค้าองค์กร
- **License ฟอนต์** — ห้ามฝัง Angsana/Cordia/Browallia ที่ไม่มีสิทธิ์ในระบบ แม้จะก๊อปมาจากเครื่อง Windows ได้จริงก็ตาม
- **Churn สูงตามฤดูกาล** — งานเอกสารประเภทนี้มักทำเป็นรอบ (สิ้นปี, จบคอร์สอบรม) ผู้ใช้อาจสมัครเดือนเดียวแล้วเลิก
  ต้องออกแบบราคาที่รองรับ pattern นี้ได้ (เช่น pay-per-use แทน subscription อย่างเดียว)
- **คนที่เจ็บปัญหาที่สุด (HR ระดับปฏิบัติการ) มักไม่ใช่คนอนุมัติงบ** — ต้องคิดเรื่อง sales motion ที่ข้ามไปหาคนอนุมัติได้

## 12. สิ่งที่ต้องทำต่อ (ลำดับความสำคัญ)

1. **ตรวจสอบตลาดกับคนจริง** — หา 10 คนที่ทำงานเอกสารแบบนี้ (HR, ธุรการฝึกอบรม) ถามความถี่ที่ทำ +
   ต้นทุนเวลาปัจจุบัน + ให้ลอง prototype จริง + ถามคำถามฆ่า "จะจ่าย 590฿/เดือนไหม" — **นี่คือ blocker ก่อนลงทุนต่อ**
2. แก้ไฟล์ prototype: ตั้งชื่อไฟล์จาก pattern + กันชื่อซ้ำ/ชื่อสงวน
3. Web Worker + cache XML เพื่อรองรับ generate จำนวนมากขึ้นในเบราว์เซอร์
4. รายงานตรวจ template อัตโนมัติ (ข้อ 9.1)
5. Backend PDF worker: merge-then-convert + Gotenberg + queue ตาม tenant
6. Pricing page + billing (เฉพาะหลังมีสัญญาณจากข้อ 1)
